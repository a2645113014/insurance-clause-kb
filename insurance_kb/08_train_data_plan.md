# 08 训练数据获取与构造方案

> 面向：Qwen3-0.6B LoRA SFT（要素抽取 / 合规判定 / 拒答三类任务）
> 前置文件：`02_clause_schema.json`（输出格式契约）、`05_sft_samples.jsonl`（模具）、`07_prompts_v2/clause_extract.prompt`（生成器）
> 版本：v1.0 ｜ 2026-09-17

---

## 0 一句话结论

**05 不是训练数据，是模具。真正的缺口是原料——条款原文，当前 0 条。**

- 拿 05 直接训练：18 条 ≈ 学不到任何东西，loss 能降但泛化为零。`loss 下降 ≠ 模型学会`。
- 拿 05 造数据：它锁定了 instruction 写法与 output 的 JSON 结构，配合强模型 + 真实条款，可批量产出 3–5k 条。
- **所以顺序不是「用 05 训练」，而是「先采条款，再用 05 当模板蒸馏」。**

## 1 三层关系

| 角色 | 具体内容 | 现状 | 量 |
|---|---|---|---|
| **模具** | 05 的 18 条 + `clause_extract.prompt` + `02_clause_schema.json` | ✅ 齐备 | 18 条种子 |
| **原料** | 真实条款原文（切分后的 chunk） | ❌ **零条** | 需 2000–5000 chunk |
| **填料** | 公开集 CUFEInse / InsQABench | 未下载 | 14430 题 / 三类任务 |

模具决定「长什么样」，原料决定「含量」，填料负责「扩面」。三者缺一不可，但**原料是第一阻塞项**。

已核实：`output/` 与 `doc/` 下现有 12 份 MD 全部是通用商品手册（hak180 产品安全手册、华为擎云 B530、Aolynk CB3048 网桥、万用表 RS-12），**无一份保险条款**。条款语料必须从零采集（清单 Phase 1.1）。

## 2 五步流水线

| 步 | 动作 | 产出 | 依据 |
|---|---|---|---|
| 1 | 采 30–50 款产品条款 | 条款 PDF + 产品注册号 + 报备文号 | `03_data_sources.csv` |
| 2 | 跑一遍导入链路（MinerU → MD → 三级切分） | 条款 chunk（含 `clause_no`、`clause_type`） | Phase 1.2–1.4 |
| 3 | few-shot 蒸馏：一条 chunk 调一次强模型 | 原始样本（16 字段 JSON） | `clause_extract.prompt` |
| 4 | 自动质检：结构 + 溯源 + 摘录三重校验 | 干净样本 | 见 §3 |
| 5 | 落盘并登记到 LLaMA-Factory | 可训练的 jsonl | §5 |

**规模换算：** 30 款产品 × 60–100 条条款 ≈ 2000–3000 条 chunk。**每条 chunk 生成 1–2 个样本**（同一条款可分别考察"全部字段"与"指定字段子集"），即可得 3–5k 条，正好对上清单 §5.3 的 A 路径目标。

**成本量级：** 3000 次调用 × 每条约 1.5k token 输入 + 0.5k 输出 ≈ 6M token。按国产强模型价格，属于可承受范围。

## 3 为什么这套数据能被程序自动验真（核心技术点）

`clause_extract.prompt` 的硬性规则 1 要求 **value 逐字摘录原文**。这条约束的副作用是：**输出可被程序逐字符验证**，从而让规模化的边际成本趋近于零。

三重校验，任一不过即丢弃该条（不进训练集，不进人工队列）：

| # | 校验 | 检查内容 | 实现难度 |
|---|---|---|---|
| 1 | 结构校验 | JSON 可解析；16 个字段一个不少；`source_clause_no` 键存在 | 低 |
| 2 | 溯源校验 | `source_clause_no` 的字符串能在 chunk 原文中找到 | 低 |
| 3 | 摘录校验 | `exclusions` / `claim_documents` / `coverage_items` 的**每一项**都能在原文中字符串命中 | 低 |

**关键推论：**

- 校验 3 是「幻觉检测器」。强模型若把 7 项免责合并成 5 项、或把「酒后驾驶」改写成「醉酒驾驶」，字符串匹配立即失败。这比人工审校可靠且零成本。
- `not_specified` 不需要校验（它没有原文可对），**但它的比例必须统计**。某一字段 `not_specified` 占比超过 70%，说明该字段在语料中本就罕见，应考虑从 16 字段里剔除，否则模型会学成"一律输出 not_specified"。
- 这套校验逻辑可直接复用到 Phase 4 的**引用准确率**评测：评测时用同一条规则判「答案里的每条断言能否回溯到真实 chunk」。一套代码，两处收益。

**人工只做抽检，不做全检：** 按 5% 抽样（约 150 条），抽查项是校验 1–3 覆盖不到的**语义正确性**——字段有没有抽错位置、条款号有没有张冠李戴。

## 4 三类任务的数据分工

| 任务 | 05 中的种子 | 扩法 | 目标规模 | 服务对象 |
|---|---|---|---|---|
| **要素抽取** | 第 1–10 行 | 条款 chunk × `clause_extract.prompt` 蒸馏 | 3–5k | 0.6B 主任务 |
| **合规判定** | 第 15–18 行 | 条款表述 × `04_negative_list_2026.json` 条目**配对** | 1–2k | 合规审查链路 |
| **拒答** | 第 11–14 行 | 跨产品/跨险种挖问题 + 空检索构造 | 0.5–1k | 拒答能力（验收 ≥85%） |

**合规判定任务的构造要点：** 配对要 1:1:1 平衡三类——真违规、真合规、条目与表述不对应（判「合规」但要提示核查）。第三类最容易漏，而它恰恰是训练「不因敏感词就判违规」的关键（对应 `compliance_check.prompt` 硬性规则 3 与 4）。

## 5 落盘目录约定

| 层 | 路径 | 内容 |
|---|---|---|
| 原始 PDF | `data/clauses/pdf/{product_code}.pdf` | 采集原件 |
| 解析后 MD | `data/clauses/md/{product_code}.md` | MinerU 产出 |
| 切分 chunk | `data/clauses/chunks/{product_code}.jsonl` | 蒸馏的输入 |
| 蒸馏原始产物 | `data/sft/raw/{task}.jsonl` | 未质检 |
| 质检通过 | `data/sft/clean/{task}.jsonl` | 待人工抽检 |
| 质检丢弃 | `data/sft/rejected/{task}.jsonl` | 保留，用于调 prompt |
| 最终数据集 | 复制进 WSL `~/LLaMA-Factory/data/` | 并在 `dataset_info.json` 登记 |

**`rejected` 必须留。** 丢弃率与丢弃原因是 prompt 迭代的唯一依据：丢弃率高且集中在某个字段，说明 `clause_extract.prompt` 对该字段的描述有歧义，改 prompt 而不是改数据。

## 6 立即可做：不等采集的链路验证

**目的不是训出可用模型，是验证 6GB 显存配置跑得通。** 两者不要混淆。

用 05 的 10 条要素抽取样例做**模板置换增强**，扩到 ~200 条：

| 置换维度 | 做法 | 扩充倍数 |
|---|---|---|
| 数字 | 90 日 → 180 日、15 日 → 20 日 | ×2 |
| 险种 | 重疾险 → 医疗险 → 寿险（调换 `coverage_items` 语义） | ×3 |
| 主体 | 我们不承担 → 本公司不承担 | ×2 |
| 字段子集 | 同一条款分别要求抽全字段 / 只抽等待期+免责 | ×3 |

这样得到的 200 条**语义是假的**（条款是拼的），只能用于：跑通 LoRA 训练、验证 liger_kernel 是否生效、确认 loss 曲线形态正常。**绝不能用于评测，也不能拿它的效果写进简历。**

## 7 工程顺序建议（有判断）

按清单，Phase 3.1 才轮到 0.6B 微调，现在连 Phase 1.1 都没开始。**不建议现在正式训练**，理由：

1. 没有真实条款 → 没有真实训练数据 → 训出来的模型没有可解释的能力边界，面试时说不清。
2. 条款切分（Phase 1.3）先落地，蒸馏输入的质量才有保证。**脏 chunk 进，脏样本出**——切分把免责条款截断了，蒸馏出来的 `exclusions` 本身就是错的，且这种错误**通不过校验 3**（不影响自动质检，但会白跑一遍）。
3. 而切分代码改完必须用真实条款验证（验收标准是抽检 50 条条款号准确率 ≥95%）。

**推荐顺序：** Phase 1.1 采条款 → 1.2 schema 落地 → 1.3 三级切分 → **这时**用刚切出来的 chunk 做蒸馏 → 训练 → 回填 Phase 3.1。

链路验证（§6）可以插在 1.1 与 1.2 之间做，纯粹为了把环境坑踩掉。
