## 0.2 三个必须提前定的设计决策

这三条不在清单里明写，但会决定后面所有代码怎么写。**先定，免返工。**

### 决策 A：新建 collection，不覆盖 `kb_chunks_v2`（✅ 已于 2026-09-18 执行）

| 方案 | 后果 |
|---|---|
| 复用 `kb_chunks_v2`、改字段 | ❌ **`kb_chunks_v2` 里的 749 条是 `D:\workspace\knowledge_base`（金融知识库项目）的生产数据 —— 改它等于破坏另一个项目** |
| **新建 `insurance_clauses` / `insurance_item_names` / `insurance_entities`** | ✅ 与金融项目物理隔离，双向零影响 |

理由有两条，**第二条比第一条更硬**（2026-09-18 实测后才明确）：

1. 主键要从 `INT64 auto_id` 换成 `VARCHAR`，本身就是破坏性变更 —— `02_clause_schema.json` 的 `versioning.breaking_change_rule` 明确写了「修改已有字段名或语义视为破坏性变更，必须重建 collection」。
2. **本机这个 Milvus 实例被两个项目共用** —— 复用旧集合名等于往别人的生产库里灌数据。

**已落地**：`.env` 的 `CHUNKS_COLLECTION` → `insurance_clauses`、`ITEM_NAME_COLLECTION` → `insurance_item_names`、新增 `ENTITY_NAME_COLLECTION=insurance_entities`、`MONGO_DB_NAME` → `insurance_kb`。

**代码侧无需任何改动**：实测全库正则搜索 `kb_chunks_v2|kb_item_names|kb002`，Python 代码里零硬编码（只有一处注释），集合名全部经 `milvus_config.py` 从 `.env` 读取。**这是本次隔离能零改代码完成的原因。**

> 关于「对照基线」：原先设想的「用旧集合当商品手册基线」已作废（那批数据不是本项目的）。Phase 2 的消融 baseline 改为**保险条款库内部的三组权重对照**（`0.8/0.2` vs `0.6/0.4` vs `0.5/0.5`，见 §4.3），不依赖任何旧集合。

### 决策 B：`auto_id` 必须改成 `False`

现有代码 `node_import_milvus.py:29` 是 `create_schema(auto_id=True)`，主键 `chunk_id INT64` 自增。

改成 VARCHAR 复合主键后，**`auto_id` 必须为 `False`，主键值由代码显式给出**。Milvus 不允许对 VARCHAR 主键开 `auto_id` —— 这是本改造最容易踩的坑，症状是建表时直接抛异常。

连带影响：`step_4_insert_collections` 里靠 `insert_result["ids"]` 回填 `chunk_id` 的逻辑**整段作废**，因为 pk 是我们自己算的。

### 决策 C：字段名以 `02_clause_schema.json` 为准 → `content` 改名 `text`

schema 里正文字段叫 `text`，现有代码叫 `content`。**不要两套并存**，按 schema 走。影响到的地方：

| 文件 | 改什么 |
|---|---|
| `node_document_split.py` | chunk 字典的 `content` → `text` |
| `node_bge_embedding.py:39,41` | `chunk["content"]` → `chunk["text"]`；拼接前缀由「商品：…，介绍：…」改为「产品：…，条款：…」 |
| `node_import_milvus.py` schema | `content` → `text`（max_length 65535 → **8192**，按 schema） |
| `node_rerank.py:31,41` | `entity.get("content")` → `entity.get("text")` |
| `node_search_embedding.py:46` / `hyde` 节点 `output_fields` | `content` → `text` |
| `node_answer_output.py:51` | `chunk.get("text")` —— **这里不用改**，它已经是 `text`（rerank 阶段已转换） |

**条款号正则** —— 三类写法必须全支持（实际语料三种混用）：

CLAUSE_NO_PATTERN = re.compile(

**中文数字归一化**（写 `clause_no_norm`）：

```python
CN_NUM = {"一":1,"二":2,"三":3,"四":4,"五":5,"六":6,"七":7,"八":8,"九":9,"十":10}
```

要处理的坑：

| 原文 | 归一化结果 | 坑点 |
|---|---|---|
| 第六条 | `6` | |
| 第十二条 | `12` | 「十二」不是「一十二」，要单独判 |
| 第二十条 | `20` | 「二十」 |
| 第二十三条 | `23` | 「二十三」 |
| **第六条之一** | **`6.1`** | ⚠️ 清单 §3.3 明确要求：**不要归一化成 `6`**，否则与第六条正文混一起 |
| 6.2 | `6.2` | 原样 |
| （一） | `一` → 转 `1` | |

**实现顺序建议**：先只做 L1（条款号切分 + 归一化），用一份真实条款跑，看抽检 50 条里条款号识别对不对（验收标准 ≥95%）。**确认 L1 准了再加 L2/L3** —— 一起上，出问题分不清是哪层的锅。

**产出字段**：每个 chunk 至少要有

```python
{
  "text": ...,              # 条款原文，禁止改写
  "clause_no": "第六条",      # 原文
  "clause_no_norm": "6",     # 归一化
  "clause_path": "第六条 > 6.2",
  "chunk_level": "L1",       # L1/L2/L3
  "chunk_seq": 1,            # 条款内切片序号（三级切分产生多片时用）
  "char_len": 123,
  "needs_review": False,
}
```

**注意 `step_4_backup_chunks`**：它写到 `output/.../backup.json`。**这条路要保留**，因为这是你排查切分质量的一手材料。另外建议再加一条：**把切分结果同时写一份到 `data/clauses/chunks/{doc_id}.jsonl`**，供 08 方案里的蒸馏使用。

**边界情况**（清单 §3.4，必须处理）：

| 情况 | 处理 |
|---|---|
| 释义引用「见 6.2 条释义」 | 保留原文（正则锚定行首，天然不会误切），在 metadata 记被引用条号 |
| 跨页条款 | 按条款号合并，**不要按页切** |
| 条款内表格（费率表/现金价值表） | 整表作为一个 chunk，`clause_type=其他` |
| 附件与正文混排 | 定位附件起始位置，附件单独处理 |
| 条款号跳号/重号 | `needs_review=True`，进人工队列 |

**验收**：抽检 50 条 → 条款号识别准确率 ≥95%，无跨条截断。

### 1.5 幂等导入

**改 `node_import_milvus.py` 的两个 step。**

#### (a) `step_3_delete_old_data` —— 幂等键要换

现在是：

```python
milvus_client.delete(filter=f"item_name == '{item_name}'")
```

改成按 `doc_id` 删（一个 doc_id 对应一份产品条款）：

```python
milvus_client.delete(filter=f"doc_id == '{doc_id}'")
```

**为什么不用 `product_code`**：`product_code` 形如 `太平洋人寿[2025]疾病保险190号`，含中文和方括号，在 Milvus 表达式里有转义风险。`doc_id` 是我们自己起的文件名，安全。**注意：项目里已经有 `app/utils/escape_milvus_string_utils.py`，如果最终决定用 `product_code`，必须套这个工具。**

#### (b) 新增 pk 构造 step

在 insert 前给每个 chunk 算 pk（`02_clause_schema.json` 定的规则）：

```python
pk = f"{doc_id}_{chunk['clause_no_norm']}_{chunk['chunk_seq']}"
```

用**流水号而非内容 hash** 做主键，因为：

- pk 稳定 → 同一条款重导两次，pk 相同 → 先删后插后 `row_count` 不变（这才是幂等）
- `content_hash` 另存一个字段，作用是**检测内容是否真的变了**（内容没变可以跳过重算 embedding，省时间）

`content_hash` 的算法（对应 schema 的 `content_hash` 字段）：

```python
import hashlib
content_hash = hashlib.sha256(chunk["text"].encode("utf-8")).hexdigest()
```

**验收**：同一份条款**导入两次**，`row_count` 不变。查询条数：

```python
c.query(collection_name="insurance_clauses", filter="doc_id == 'cpic_重疾_金佑人生'", output_fields=["count(*)"])
```

> 如果查条数遇到 `Cannot invoke RPC on closed channel` 或 count 与预期对不上，见 skill `milvus-data-ops`。
