# 保险条款知识库改造清单

> 目标项目：`WH260713_knowledge_base`（现为通用商品知识库，掌柜智库）
> 改造方向：通用商品手册 → **保险条款知识库 + 合规审查 Agent**
> 配套文件：`02_clause_schema.json`、`03_data_sources.csv`、`04_negative_list_2026.json`、`05_sft_samples.jsonl`、`06_eval_cases.csv`、`07_prompts_v2/`
> 版本：v1.0 ｜ 2026-09-17

## 0 适用范围与不做的事

**做：** 条款原文检索、条款要素抽取、条款级溯源引用、条款表述合规审查、无依据拒答。

**不做（合规红线，写进代码也要写进文档）：**

| 禁止项 | 原因 |
|---|---|
| 产品推荐、性价比对比 | 属销售行为，需持牌资质 |
| 保费测算、投保方案建议 | 属保险销售建议 |
| 理赔金额承诺、「一定能赔/肯定不赔」 | 属结论性承保判断，且无法验证 |
| 泛保险知识百科式问答 | 不需要检索私有文档，RAG 价值不成立 |

超出范围的问题一律走 `out_of_scope` 分支拒答，指向持牌从业人员或官方客服。

## 2 Collection 设计

### 2.1 三个 collection 的职责划分

| collection | 存什么 | 检索方式 | 谁在用 |
|---|---|---|---|
| `insurance_clauses` | 条款原文切片 + 完整 metadata | 混合检索（dense+sparse） | 问答链路、抽取链路 |
| `insurance_entities` | 产品名、险种、责任名、疾病名等标准实体 | 向量名匹配（阈值对齐） | 指代消解与实体确认节点 |
| `compliance_rules` | 负面清单 105 条 + 监管规章 + 处罚案例 | 混合检索 | 合规审查链路 |
| `insurance_rules`（MongoDB，非向量库） | 结构化理赔规则表 | 键值精确查询 | Function Calling 工具 |

`insurance_rules` 刻意**不放进 Milvus**：它需要的是确定性查询（按险种 + 事故类型取材料清单），不是相似度检索。放进向量库会让一个可精确回答的问题变成概率问题。

### 2.2 `insurance_clauses` 字段定义

完整定义见 `02_clause_schema.json`，此处只列关键字段与设计意图。

| 字段 | 类型 | 索引 | 设计意图 |
|---|---|---|---|
| `pk` | VARCHAR(128) | 主键 | `{product_code}_{clause_no_norm}_{chunk_seq}`，先删后插的幂等依据 |
| `vector` | FLOAT_VECTOR(1024) | HNSW/COSINE | BGE-M3 dense |
| `sparse` | SPARSE_FLOAT_VECTOR | SPARSE_INVERTED_INDEX/IP | BGE-M3 sparse，**条款术语精确命中靠它** |
| `text` | VARCHAR(8192) | — | 条款原文，禁止改写 |
| `clause_no` | VARCHAR(32) | — | 条款号原文（「第六条」/「6.2」） |
| `clause_no_norm` | VARCHAR(32) | — | 归一化编号（「6」/「6.2」），用于排序与引用拼接 |
| `clause_type` | VARCHAR(32) | INVERTED | **核心新增字段**，支持"只在责任免除里搜" |
| `clause_path` | VARCHAR(256) | — | 层级路径，如「第六条 > 6.2」 |
| `company` / `product_name` / `product_code` | VARCHAR | INVERTED | 产品维度过滤，多产品库隔离的前提 |
| `insurance_type` / `design_type` | VARCHAR | INVERTED | 险种与设计类型过滤 |
| `filing_no` | VARCHAR(128) | — | 报备文号，回答"是否备案"类问题的依据 |
| `page_no` | INT64 | — | 前端跳原文 |
| `chunk_level` | VARCHAR | — | 标记由哪级切分产生（L1/L2/L3），排查切分质量 |
| `content_hash` | VARCHAR(64) | — | sha256，幂等 |
| `needs_review` | BOOL | — | 低置信度切片进人工抽检队列 |

**与现状代码的对应改动：**
- `app/clients/milvus_utils.py`：字段定义新增 `clause_no`、`clause_no_norm`、`clause_type`、`clause_path`、`company`、`insurance_type`、`design_type`、`filing_no`、`chunk_level`、`needs_review`
- `app/conf/milvus_config.py`：新增 `insurance_clauses`、`insurance_entities`（由 `kb_item_names` 改造）、`compliance_rules` 三个 collection 名与索引参数
- `app/import_process/agent/nodes/node_import_milvus.py`：主键构造规则改为上述复合主键

### 2.3 检索权重必须重新标定

现状 `WeightedRanker(0.8, 0.2)` 是给商品手册调的。保险条款是法律文本，**术语精确匹配的价值显著上升**：

- 起始建议：`WeightedRanker(0.6, 0.4)`，配 `norm_score=True`
- 但**必须用消融实验定标**，不要照搬。对照三组：0.8/0.2、0.6/0.4、0.5/0.5，指标取 Recall@k 与 MRR
- 断崖式动态 TopK（相对阈值 0.5 / 绝对阈值 2）保留，但条款 chunk 更自包含，绝对阈值可下调到 1 观察效果

## 3 切分策略改造（最关键的技术改动）

### 3.1 现状问题

现在是 `node_document_split.py` 里的「Markdown 标题初切 + RecursiveCharacterTextSplitter(200/20)」。用在保险条款上有三个硬伤：

1. **条款不以 Markdown 标题组织。** 保险条款的层级是「第X条 → （一）→ 1.」，PDF 转 MD 后往往只是普通段落，标题初切几乎切不动，全落到定长切分。
2. **200 字符会把一条完整条款拦腰截断。** 一条免责条款可能 500+ 字，切碎后单条免责情形与它的适用条件分离，检索到「酒后驾驶」却检索不到「我们不承担给付保险金的责任」。
3. **条号信息丢失。** 切完不知道这段属于第几条，导致无法生成「⟨第六条⟩」这种可溯源的引用——**这是整个改造中最要命的一条**。

### 3.2 三级切分

| 层级 | 依据 | 何时触发 | 产出 |
|---|---|---|---|
| **L1 条款号** | 正则识别「第X条 / 第X条之一 / X.X / X.X.X」 | 默认主切分 | 一个 chunk = 一条完整条款 |
| **L2 分项** | 章内序号「（一）（二）」「1. 2.」「（1）（2）」 | L1 切片超过上限字符数时 | 按分项切，chunk 间共享 `clause_no` |
| **L3 兜底** | 句子边界 + 定长 | L2 后仍超长 | 保留 `clause_no`，`chunk_level=L3`，`needs_review=true` |

**切分上限建议：** L1 单条超过 1200 字符才下探 L2；L2 单条超过 800 字符才下探 L3。条款 chunk 的目标长度在 300–800 字符，比商品手册长得多——**别沿用 200**。

### 3.3 条款号正则要点

覆盖三类写法（实际语料里三种混用，必须全支持）：

```
第X条 / 第X条之一          → 中文数字或阿拉伯数字
X.X / X.X.X               → 章节式编号
（一）/ 1. / （1）         → 分项编号
```

配套要做两件事：

1. **中文数字归一化**：「第六条」→ `6`、「第十二条」→ `12`，写入 `clause_no_norm`。注意「第X条之一」要归一化为 `6.1`，不要归一化成 `6`，否则会与第六条正文混在一起。
2. **条款类型识别**：用 `02_clause_schema.json` 里 `clause_type.match_keywords` 的关键词表命中，写入 `clause_type`。命中多个时按优先级取（责任免除 > 保障责任 > 保险金申请 > 其他）。

### 3.4 必须处理的边界情况

| 情况 | 处理方式 |
|---|---|
| 释义引用（「见 6.2 条释义」） | 保留原文，同时在 metadata 记录被引用条号，供多跳检索 |
| 跨页条款 | 按条款号合并，不要按页切 |
| 条款内的表格（费率表、现金价值表） | 不切碎，整表作为一个 chunk，`clause_type=其他`，避免表格结构破坏 |
| 附件与条款正文混排 | 用文档结构定位附件起始位置，附件单独处理 |
| 条款号跳号或重号 | 记入 `needs_review`，人工确认后修正 |

## 4 Prompt 改法

6 个现有 prompt 全部需要改，另新增 2 个。**改写后的文件在 `07_prompts_v2/`，可直接对照替换。**

### 4.1 现有 6 个的改法对照

| 文件 | 现状 | 改什么 | 为什么 |
|---|---|---|---|
| `answer_out.prompt` | 「尽量基于参考内容，不要编造」 | 加入**强制条款号引用**、**矛盾前置纠正**、**四类禁止输出**、**固定免责声明** | 「尽量」是软约束，模型会漏引用。法律文本场景必须硬约束，且引用条款号是合规要求不是加分项 |
| `item_name_recognition.prompt` | 识别「商品名称与型号」 | 改为识别**保险产品备案名称**，优先依据产品注册号/报备文号 | 保险产品名的权威标识是注册号（如「太平洋人寿[2025]疾病保险190号」），不是型号 |
| `rewritten_query_and_itemnames.prompt` | 提取商品名 + 改写问题 | 增加**只给险种不给产品时返回空**、**保留条款主题词**、**追问还原为独立问题** | 用户说「重疾险」时若猜一个具体产品，会答非所问；条款主题词是检索的关键线索，改写时丢掉等于自断召回 |
| `hyde_prompt.prompt` | 生成「简洁的回答范文」 | 改为生成**假设性条款表述**（条款文体），并要求非条款问题输出 `NOT_A_CLAUSE_QUERY` | **这是本次改动里收益最大的一个。** 用户问「多久能赔」是口语，条款写「自收到保险金给付申请书之日起」是法律文体，HyDE 生成口语化答案会把向量推向错误方向；生成条款文体才能贴近目标语料分布 |
| `image_summary.prompt` | 概括图片用于标题 | 增加**表格必须写明表名与维度**、区分图表/结构图/条款截图 | 条款 PDF 里的图主要是费率表与现金价值表，只写「一张表格」的标题无法被检索命中 |
| `product_recognition_system.prompt` | 「你是商品识别专家」 | 改为**保险产品识别**，规则与 `item_name_recognition` 对齐 | 单一职责，输出格式统一 |

**关键约束：占位符名字一个都不能改。** 现有代码按 `{context}` `{history}` `{item_names}` `{question}` `{file_title}` `{history_text}` `{query}` `{rewritten_query}` `{root_folder}` `{image_content[0]}` `{image_content[1]}` 做 format，改名会直接抛 KeyError。改写版已全部保留原占位符。

### 4.2 新增 2 个 prompt

| 文件 | 用途 | 服务对象 |
|---|---|---|
| `clause_extract.prompt` | 条款要素抽取（16 个字段 → JSON） | 微调 0.6B 模型 |
| `compliance_check.prompt` | 对照负面清单判定违规 | 大模型 + 负面清单检索 |

两个都有同一条硬规则：**必须显式输出「未约定」而不是省略字段**。这是拒答能力的数据基础——模型只有学会说 `not_specified`，线上才会说「依据现有条款无法回答」。

## 5 数据来源

完整清单（含 URL、采集难度、许可）见 `03_data_sources.csv`，此处给结论。

### 5.1 条款语料——公开且充足

| 优先级 | 来源 | 拿到什么 |
|---|---|---|
| P0 | 保司官网「公开信息披露 → 产品条款」 | 条款 PDF 直链 + 产品注册号 + 报备文号 |
| P0 | 中保协官网「保险产品」栏目 | 全行业产品条款检索入口 |
| P0 | 中保协示范条款公告 | 标准条款 docx 直链（2026 修订版定期寿险/终身寿险） |
| P1 | 互联网保险信息披露页 | 条款 + 费率表 + 备案编号 + 销售状态（元数据最全） |
| P2 | 中保协财险自主注册产品查询（`cxcx.iachina.cn`） | 财险条款，**需注册登录** |

**已核实的最优元数据模板**是太平洋人寿的互联网保险产品信息页，四列结构正是我们需要的 schema 骨架：备案产品名称 / 产品条款 / 报备文件编号或批复文号 / 产品注册号。

**规模建议：30–50 款产品、2000–5000 个条款 chunk。** 不要贪多——MinerU 每份 PDF 都要跑一遍解析，堆量只会变成解析负担，而评测指标不会因此变好。领域内深度优先于数量。

### 5.2 合规语料——负面清单 105 条

`04_negative_list_2026.json` 已整理为结构化 JSON，四大类：

| 分类 | 条数 | 内容 |
|---|---|---|
| 产品条款表述 | 27 | 文字表述不规范、误导销售隐患、理赔材料不合理 |
| 产品责任设计 | 23 | 设计雷同、产品异化、责任与定义不符 |
| 产品费率厘定及精算假设 | 36 | 费率不真实、精算假设偏离实际、生命表使用不当 |
| 产品报送管理 | 19 | 备案材料漏报、报行合一、僵尸产品清理 |
| **合计** | **105** | 与监管公布条数一致（27+23+36+19=105） |

2026 版相对 2025 版新增 2 条（第 27 条处方审核主体、第 86 条分红红利分配比例），修订 7 条。JSON 里 `is_2026_new` / `is_2026_modified` 已标注。

**这份文件一物三用：** ① 入 `compliance_rules` collection 做合规审查；② 作为 SFT 合规判定任务的标签体系；③ 作为评测集出题依据。

### 5.3 微调语料——六条路径

| # | 路径 | 规模 | 难度 |
|---|---|---|---|
| **A** | 条款 → 要素抽取对（强模型蒸馏 + 人工抽检） | 3–5k | 低，自造 |
| **B** | 条款表述 vs 负面清单 → 合规判定标签 | 1–2k | 低，自造 |
| **C** | 拒答负样本（跨产品/跨险种挖问题） | 0.5–1k | 低，自造 |
| D | 裁判文书 → 争议焦点/涉案条款/法院认定 | 0.5–1k | 中，需脱敏 |
| E | 公开集复用（CUFEInse / InsQABench） | 全部 | 低 |
| F | RAG 拒绝采样自蒸馏 | 0.5–1k | 中 |

**起步组合：A + C + E。** `05_sft_samples.jsonl` 已给 18 条样例覆盖这三类（10 条要素抽取、4 条拒答、4 条合规判定），可直接作为格式模板与 few-shot 种子。

### 5.4 评测集——现成的底子

| 来源 | 规模 | 许可 | 定位 |
|---|---|---|---|
| **CUFEInse** | 14,430 题 / 5 维度 | Apache-2.0 | 主评测集。`huggingface.co/datasets/CUFEInse/CUFEInse`，GitHub 同名仓库 |
| **InsQABench** | 中文保险 QA 三类任务 | 见仓库 | 补充评测 + 微调种子。`github.com/HaileyFamo/InsQABench` |
| 自造 | 200 题 | — | 条款级溯源与拒答能力，公开集覆盖不到 |

`06_eval_cases.csv` 已给 41 条示例用例，按五类组织并留出扩展位：`fact_qa` 事实问答 16 条、`refuse` 应拒答 8 条、`hallucination_bait` 幻觉诱导 5 条、`coref` 多轮指代 5 条、`compliance` 合规判定 4 条，外加 3 条消融探针。按同样字段结构补充到 200 题即可。

## 8 合规红线

1. **条款版权归保险公司。** 公开可查 ≠ 可再分发。项目展示只放少量样例 + 采集说明，不打包发布语料。
2. **裁判文书展示必须脱敏**（当事人姓名、案号、法院）。
3. **输出恒带免责声明**，模板固定在 `answer_out.prompt` 里，不允许被 prompt 注入绕过。
4. **私有化叙事的正确口径**：条款是公开的，不能拿它当私有化理由。真正需要私有化的是**内部理赔规则 + 客户保单与理赔材料**。统一话术：*"条款我做成可溯源的公开合规引用层；真正需要私有化的是内部规则库和客户保单数据，所以整体走本地部署。"*
5. **负面清单以监管原文为准。** `04_negative_list_2026.json` 条文整理自公开转载，用于工程实践无碍，对外正式合规判定须核对监管原文。

## 9 面试话术要点

### 9.1 一个可以直接引用的市场事实

CUFEInse（中央财经大学保险学院 + 中国精算研究院，14,430 题）的公开测评结果显示，**「保险安全合规」是所有模型的最弱维度**：

| 模型 | 总分 | 保险安全合规 |
|---|---|---|
| AntGroup Finix-S1-32B | 89.51 | 86.78 |
| Gemini-2.5-Pro-0617 | 85.11 | 78.80 |
| DeepSeek-R1-0528 | 84.20 | 75.17 |
| Qwen3-235B-A22B-instruct | 82.66 | 73.93 |
| Qwen3-32B-think | 80.34 | **65.63** |
| GPT-4o-1120 | 79.71 | **69.33** |
| Fin-R1 | 71.46 | **67.09** |

测评选出的三大共性瓶颈是：**保险精算、核保核赔决策、文案合规性**。

**这直接支撑你的项目定位**：把重心放在"条款级合规审查"上，就是在打行业公认的最弱项。这句话可以直接写进面试自我介绍。

### 9.2 三条可以讲的硬技术点

1. **HyDE 的文体改造。** 常规做法是让 HyDE 生成"假设答案"，但保险条款场景下口语与法律文体差异极大，我改成生成"假设性条款表述"，让假设文档贴近目标语料的文体分布。消融实验显示 Recall@k 提升 X 个点。
2. **双层知识结构。** 条款是法律层（公开、稳定、可溯源），理赔规则是执行层（内部、高频迭代、条件分支）。两层分别用检索和工具调用承载，而不是混在一个 collection 里——因为规则需要确定性查询，用向量检索是错的。
3. **条款级溯源。** 切分以条款号为主键而非字符长度，使每个 chunk 天然携带 `clause_no`，答案里的每个断言都能回溯到「第六条」这种可验证的出处。这是合规场景的硬要求。

### 9.3 项目定位一句话

> 私有化行业知识 Agent：条款级混合检索 + 窄任务微调模型（要素抽取/合规判定）+ 工具调用 + 评测闭环，落地在保险条款合规审查场景。
