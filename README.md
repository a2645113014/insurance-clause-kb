# 保险条款知识库与合规审查 Agent

> 面向人身险**条款原文**的检索问答与合规审查智能体。
> 双 LangGraph 链路（导入 / 查询）+ 四套存储 + 规划式（Planner）四分支路由，
> 把「RAG 能答」和「RAG 敢担责」拆开做：**答案必须逐句回引条款号，无依据必须拒答**。

`Python 3.11` · `LangGraph` · `FastAPI` · `Milvus` · `MongoDB` · `BGE-M3 + bge-reranker-large` · `qwen-max`

## 1. 项目定位

一个**通用商品手册知识库**的改造项目。原系统面向设备说明书做 RAG 问答；本项目把它整体改造成保险领域知识库，并**新增了原系统没有的能力：条款表述合规审查**。

改造不是换语料，而是换了整条链路的**正确性判据**：

| 维度 | 改造前（通用商品） | 改造后（保险条款） |
|---|---|---|
| 切分依据 | Markdown 标题 + 200 字符定长 | **条款号结构三级切分**（章 → 条 → 款） |
| 检索结果 | 文本片段 | 文本片段 + **条款号** + 产品名 + **条款类型** |
| 生成约束 | 「尽量基于参考内容」 | **强制逐句引用条款号**，无依据必须拒答 |
| 实体对齐 | 商品名 | 保险产品名（台账为单一事实来源） |
| 结构化查询 | — | **理赔材料 / 时限走 MongoDB 键值精确查询**，不进向量库 |
| 新增能力 | — | **合规审查**（对照监管负面清单 105 条） |
| 评测 | 无 | 检索标注集 276 条 + 合规金标 27 条 + 配置消融 |

一条核心判断贯穿全项目：

> **能精确回答的问题，不要交给相似度。**
>
> 理赔材料、理赔时限、指定条款号的内容，目标唯一确定 —— 这类问题走键值查询与确定性过滤；只有「这个说法在条款里怎么讲的」这类语义问题才走向量检索。把确定性需求塞进概率链路，是这类系统最常见也最难发现的错误来源。

### 3.2 模型层设计要点

- **BGE-M3 单次编码产出双向量**：稠密向量承担语义召回，稀疏向量承担**条款术语精确命中**（「等待期」「现金价值」这类词必须字面命中）。两者在 Milvus 内以 `WeightedRanker(0.8, 0.2)` 融合。模型开启原生 L2 归一化，单位化后内积等价余弦，检索更快。
- **cross-encoder 与 bi-encoder 分工**：BGE-M3 负责粗排召回，`bge-reranker-large` 负责精排。两者量纲不同（前者是余弦相似度 ∈ [0,1]，后者是 **logits，可为负**）—— 这个差异后面成了本项目两个 P0 缺陷的根源，见 [§9](#9-关键设计决策)。
- **模型单例 + 启动预热**：向量模型在 FastAPI `lifespan` 阶段于线程池内串行加载一次，避免多请求并发触发首次加载竞争（`from_pretrained` 依赖进程级全局状态，并发会互相破坏）。

### 3.3 配置层设计要点

三套独立配置面板，全部从 `.env` 读取，且每个面板都暴露一个 `signature()` 配置指纹：

| 面板 | 管什么 | 指纹示例 |
|---|---|---|
| `app/conf/retrieval_config.py` | 检索层 10 参数（融合权重 / HyDE / TopK / 断崖阈值 / 联网模式） | `w0.8-0.2_hyde1_gapabs2_gapratio0.5_lim5_webfallback_webmax2` |
| `app/conf/rule_config.py` | 规则层开关与关键词参数 | `rule1_fb1_kw19x1_insurance_rules` |
| `app/conf/compliance_config.py` | 合规层候选条数 / 兜底策略 | `comp1_k12_uni1_scope1_max40_compliance_rules` |

**为什么指纹是必需的**：消融实验要对比不同配置的跑分。如果没有指纹，报告文件会互相覆盖、结果无法回溯到配置。指纹被写进评测报告文件名（`compliance_eval_<指纹>_<模式>.json`）与日志首行，每一行跑分都能反查到当时生效的全部参数。

三个面板的解析器（`_parse_bool` / `_parse_int` / `_parse_enum` / `_parse_weights`）**刻意共用同一套实现** —— 否则会出现「同一个 `.env` 写法在 A 面板能解析、在 B 面板静默回落默认值」这类极难排查的不一致。解析失败一律**告警 + 回落默认值**，绝不静默吞掉。

## 4. 系统架构

### 4.1 导入链路（LangGraph · 7 节点）

```
                    ┌──────────────────┐
            文件 ──▶│    node_entry    │  入口：识别 .pdf / .md，登记 task 状态
                    └────────┬─────────┘
                             │ 条件边：按文件类型分流
              ┌──────────────┴──────────────┐
        (.md) │                             │ (.pdf)
              ▼                             ▼
     ┌─────────────────┐          ┌──────────────────┐
     │   node_md_img   │◀─────────│  node_pdf_to_md  │  PyMuPDF 主路，
     │ 图片提取→MinIO  │          │  （MinerU 兜底）  │  字体缺 ToUnicode 才走云
     └────────┬────────┘          └──────────────────┘
              │
              ▼
     ┌──────────────────────┐
     │ node_document_split  │  条款号锚定 + 三级切分 → 补 clause_no / clause_type
     └──────────┬───────────┘
                ▼
     ┌────────────────────────────┐
     │ node_item_name_recognition │  产品名解析：**台账优先**，LLM 兜底并清洗
     └──────────┬─────────────────┘
                ▼
     ┌───────────────────┐
     │ node_bge_embedding│  BGE-M3 批量编码（稠密 + 稀疏）
     └────────┬──────────┘
              ▼
     ┌────────────────────┐
     │ node_import_milvus │  27 字段写库，按 doc_id 先删后插 → 幂等
     └────────────────────┘
```

**两个关键设计**

1. **条款号锚定切分**：不按固定字符数切，而是先识别「第 N 条 / N.M」锚点，再在锚点间按层级贪心合并。顶层只认全角 `．` 与 `第N章`，锚点识别排除 `%‰` 和右括号（否则「占比 30.5%」会被误当条款号）。
2. **幂等靠主键**：`pk = {doc_id}_{clause_no_norm}_{chunk_seq}`，导入时按 `doc_id` 先删后插。重复导入不产生副本，可随时安全重跑。

### 4.2 查询链路（LangGraph · Planner 四分支）

```
                        ┌───────────────────────────┐
                 提问 ─▶│  node_item_name_confirm   │  产品名对齐
                        │  insurance_item_names 向量 │  WeightedRanker(0.8, 0.2)
                        └─────────────┬─────────────┘
                                      │
        ┌───────────────┬─────────────┼───────────────────────┐
        │               │             │                       │
   (产品名歧义)     (合规审查)     (理赔意图)              (其余问题)
        │               │             │                       │
        ▼               │             ▼                       ▼
 ┌─────────────┐        │      ┌─────────────┐      ┌──────────────────────┐
 │ 澄清直出     │        │      │node_rule_tool│      │  三路检索并行         │
 │ node_answer │        │      │ MongoDB 键值 │      │  ① 原问题混合检索     │
 │  _output    │        │      │ 精确查询     │      │  ② HyDE 改写后检索    │
 └─────────────┘        │      └──────┬───────┘      │  ③ MCP 联网（三态）   │
                        │             │              └──────────┬───────────┘
                        │             │                         ▼
        ┌───────────────┘             │                  ┌─────────────┐
        │                             │                  │  node_rrf   │ RRF 融合 k=60
        │  (用户已内联条款原文)         │                  └──────┬──────┘
        │  (只给产品/条款号) ───────────┼─────────────────────────┤
        ▼                             │                         ▼
 ┌────────────────────┐               │                  ┌─────────────┐
 │ node_compliance_   │◀──────────────┼──────────────────│ node_rerank │ 按来源分组断崖 TopK
 │      check         │◀ ─ ─ ─ ─ ─ ─ ─┤  先检索取回原文      └──────┬──────┘
 │ 105 条负面清单比对  │               │                         │
 └─────────┬──────────┘               │                         │
           │                          ▼                         ▼
           └─────────────────▶ ┌─────────────────────────────────┐
                               │      node_answer_output         │ 拼上下文 → qwen-max
                               │  + 免责声明 + SSE 推送 + 历史落库 │
                               └─────────────────────────────────┘
```

**为什么合规分支要「两段式」**：合规审查需要「待审表述」。用户可能直接贴条款原文（此时不该检索，直奔合规节点），也可能只说「审查《XX 产品》第 1.4 条」（此时必须先检索把原文取回来，rerank 之后再转入合规节点）。用条件边实现这一跳，而不是新建第二张图 —— 保持单图，节点与状态复用。

**为什么规则分支跳过全部检索**：理赔材料清单是「按险种 + 事故类型」唯一确定的。如果让它也走向量检索，可能召回**同公司其他产品**的材料清单 —— 那是跨产品的业务性错误。这条分支直接走 MongoDB，一条检索都不发。

### 4.3 四套存储的职责边界

| 存储 | 位置 | 内容 | 访问方式 | 谁在用 |
|---|---|---|---|---|
| `insurance_clauses` | Milvus | 条款切片 + 27 字段元数据 | 混合检索（dense + sparse） | 问答链路 |
| `insurance_item_names` | Milvus | 保险产品名索引 | 向量名匹配（带阈值对齐） | 指代消解 |
| `insurance_rules` | MongoDB | 结构化理赔规则 | **键值精确查询** | Function Calling 工具 |
| `compliance_rules` | MongoDB | 监管负面清单 105 条 + 向量 | 三路召回 + LLM 判定 | 合规审查链路 |
| `chat_message` | MongoDB | 会话历史 | 按 session_id 查询 | 多轮上下文 |
| `insurance_entities` | Milvus | 险种 / 责任 / 疾病名 | — | 设计预留，未启用 |

**为什么理赔规则刻意不进向量库**：它需要的是确定性查询（按险种 + 事故类型取材料清单），不是相似度检索。放进向量库会把一个可精确回答的问题变成概率问题。

> ⚠️ **命名前缀 `insurance_` 是隔离刚需，不是审美选择**。本项目开发机上的 Milvus 实例与另一个金融知识库项目**共用同一个 19530 端口**。所有集合一律加 `insurance_` 前缀并配独立 MongoDB 库名 `insurance_kb`，确保双向零污染。历史遗留集合一律不读写。

### 4.4 服务面

| 服务 | 入口 | 端口 | 主要接口 |
|---|---|---|---|
| 导入服务 | `app/import_process/api/file_import_service.py` | 8000 | 文件上传 / 任务状态 / 节点进度 |
| 查询服务 | `app/query_process/api/query_service.py` | 8001 | `/query`、`/stream/{session_id}`、`/history`、`/chat.html` |

## 5. 数据资产现状（实测）

> 以下数字均为 2026-09-24 只读查询实测，非设计目标值。

### 5.1 条款库

| 项 | 值 |
|---|---|
| 切片总数 | **966** |
| 覆盖产品 | **17** 款（18 份 PDF，1 份因字体缺失解析失败） |
| 唯一 clause_no | **216** |

**`clause_type` 分布**（条款类型识别的落地效果）：

| 类型 | 切片数 | 占比 |
|---|---|---|
| 释义 | 291 | 30.1% |
| 保障责任 | 162 | 16.8% |
| 合同构成与效力 | 109 | 11.3% |
| **其他（enum 内确无类别）** | **93** | **9.6%** |
| 保险费 | 55 | 5.7% |
| 保险金给付 | 40 | 4.1% |
| 保险金申请 | 39 | 4.0% |
| 现金价值与退保 | 33 | 3.4% |
| 争议处理与法律适用 | 27 | 2.8% |
| 责任免除 | 24 | 2.5% |
| 其余 6 类 | 87 | 9.3% |

**「其他」从改造初期的 61.3% 降到 9.6%**。残余的 93 条是 enum 里确实没有对应类别的（如「健康管理服务」「其他需要关注的事项」），保持为「其他」比硬塞进某个类更正确 —— 分类器不做无依据的归类。

|---|---|---|

| `compliance_rules` | **105** | 4 大类：费率厘定 36 / 报送管理 19 / 销售宣传 23 / 条款表述 27；16 个 scope 标签 |

### 5.3 评测集

| 文件 | 条数 | 说明 |
|---|---|---|
| `data/eval/retrieval_cases.jsonl` | **276** | 检索标注集，双门质检（锚点存在性 + 唯一性） |

### 5.4 语料说明

条款 PDF **不入库**（版权归保险公司，公开可查 ≠ 可再分发）。仓库只保留：

- `data/clauses/sources.csv` —— 18 款产品的元数据台账（保司 / 险种 / 产品名称 / 报备文号 / 来源 URL / SHA256）
- `data/collect_clauses.py` —— 从保司公开信息披露页抓取条款 PDF 的采集器（幂等、限速 1s/次）

复现语料：跑 `collect_clauses.py` 即可按台账重新采集。

> 台账的「产品名称」列不只是元数据 —— 它是 **`item_name` 的单一事实来源**。这个字段同时是三套存储的关联键，必须确定性，因此由 `app/utils/ledger_utils.py` 统一读取，禁止各处自行解析（细节见 §9）。

## 6. 目录结构

```
insurance-clause-kb/
├── app/
│   ├── conf/                  # 三套配置面板（检索 / 规则 / 合规）+ 各服务连接配置
│   ├── core/                  # 日志（loguru 分级）、prompt 加载器
```

## 8. 评测体系

### 8.1 检索层

**标注集构造**（`test/09`）：从语料中**反向生成**问题 —— 先按锚点表定位条款，再让 LLM 生成「只能由这一条回答」的问题，最后过双门质检（锚点在语料中真实存在 + 该问题唯一对应这一条）。这样构造的标注集是 **grounded 的**，不会出现「标准答案定位不到、Recall 算不出来」的情况。

**核心结论**（276 条标注集）：

| 实验 | 结论 |
|---|---|
| 融合权重消融 | **权重不是有效杠杆** —— 三组配置差异 ≤ 0.7pp，19/276 条 top1 抖动，属等价解，保持 `0.8/0.2` |
| HyDE 开关 | **有效，保持开启** —— R@3 **+5.44pp** |

> ⚠️ **早期评测集已废弃**：初版 `06_eval_cases.csv` 用中文条号（「第六条」）写标准答案，而语料里全是 `N.M` 格式，且未绑定产品 —— 这类标注集算出的指标没有意义。教训：**验收用例必须先在语料里 grounded 一遍**。

### 8.2 合规层

**金标组成**：正例 14（确属违规的条款表述）/ 负例 10（正常条款，不该被判违规）/ 边界 3。

**四个指标**：

| 指标 | 含义 | 基线值 |
|---|---|---|
| 违规判定率 | 正例中被正确判为违规的比例 | **1.0** |
| 条号引用命中率 | 判定所引条号与金标一致的比例 | **1.0** |
| 误判违规率 | 负例中被错判为违规的比例 | **0.0** |
| 编造条号数 | 引用了不在召回列表里的条号 | **0** |
| 金标平均位次 | 金标条目在召回清单里排第几（连续量） | 2.82 |
| 全金标召回率 | 分母含边界组（关掉兜底路才会下降） | 1.0 |

**配置消融**（17 条带金标用例）：

| 配置 | 全金标召回率 | 平均条数 | 金标位次 |
|---|---|---|---|
| base | 1.0 | 40.0 | 2.82 |
| k6 / k24 | 1.0 | 40.0 | 2.71 / 3.18 |
| no_universal | 1.0 | **14.5** | 2.47 |
| no_scope | **0.9412** | 40.0 | **1.69** |

**三条结论**：

1. **`COMPLIANCE_TOP_K` 在当前兜底策略下是死旋钮** —— k6/k12/k24 输出条数全是 40（等于 `MAX_ITEMS`）。通用兜底条目有 59 条，一路就填满上限，top_k 只改顺序不改集合。要它生效必须先降 `MAX_ITEMS` 或关掉通用兜底。
2. **`INCLUDE_SCOPE_MATCH` 是唯一真有取舍的旋钮** —— 关掉后全金标召回 1.0 → 0.9412（漏一条），但金标位次 2.82 → 1.69。默认保持开启。
3. **`INCLUDE_UNIVERSAL` 在当前金标集上是纯成本** —— 召回不变、条数砍 64%、位次还改善。**但默认仍然保持开启**：17 条金标测不出「适用但语义不像」的长尾，而合规场景下**漏检的代价远大于多喂噪音**。要关它，先扩金标集。

### 8.3 关于「指标饱和」

第一轮合规召回评测报「召回率 1.0」，看起来很完美。但每条用例都恰好召回 40 条（等于条数上限），于是拆开来源分布：

> 1080 个条目位里，只有 **324** 个来自向量路，**710** 个是通用兜底回填。

指标是真的，但它是被兜底「填」出来的 —— 更严重的是**六组消融配置在这个指标上全是 1.0，配置之间完全不可区分**，「top_k 该取几」这个问题根本答不出来。

修法是补两个有区分度的口径：**金标位次**（连续量）与**全金标召回率**（分母含边界组）。过程中踩到两个坑，都已固化在代码注释里：

- 位次若只在计分正例上算，六组又全是 1.50（金标都在第 1~2 位）→ 必须覆盖带金标的边界用例。
- 分母必须取「带金标的用例数」，若取「命中的用例数」，漏掉的那条会被排除出分母 → 召回率恒为 100%。

## 9. 关键设计决策

以下每条都是开发过程中**被实测数据推翻过初版实现**之后确立的，不是纸面设计。

### 9.1 联网结果绝不与条款切片混池重排

**现象**：问「某产品的保险期间是几年」，条款原文明确写「保险期间为 11 年」，但答案给出「保障期有 4 种选择：11/15/20/30 年」，并引用了一个**条款里根本不存在的条号**。

**根因**：联网片段与本地条款被合进同一个 rerank 池统一打分。但 **bge-reranker 返回的是 logits，不是相似度**：

| 内容类型 | 实测分数 |
|---|---|
| 网页标题 + 营销文风 | **+2.59 / +3.49 / +3.81** |
| 规范条款句式 | **−0.85 ~ −7.32** |

模型对「营销文风」系统性给正分，对「规范条款句式」给负分 —— 于是联网软文**稳定占据 top1**，再叠加断崖 TopK 把本地切片清零，模型最终拿一段互联网营销文案当条款依据。

**修法**：`step_3_topk` **按 `source` 分组**，本地组走断崖，联网组独立限额且仅当本地一条都没命中时才兜底。开关 `WEB_SEARCH_MODE` 做成三态：

| 取值 | 行为 |
|---|---|
| `off` | 完全不发起联网检索 |
| `fallback`（默认） | 照常检索，但**仅当本地全空时**才拿它兜底 |
| `always` | 与本地结果一起进上下文（仅留给消融做对照） |

### 9.2 断崖判据必须分两个度量空间

动态 TopK 用「相邻分数落差」判断断崖。原判据是 `rel = gap / |score1|` —— 对负 logits 取绝对值等于拿「离零的距离」当分母，落差被系统性放大：

> 实测 top1→top2 的 `gap` 只有 1.2166，但算出的 `rel = 0.982`（阈值 0.5），于是断崖在第 1 个位置就触发，`topk` 被砍到 1。

**修法**：**两个判据用两个空间**。

- 相对判据 `rel` 移到 **min-max 归一化空间**后再比较（消除负号影响）
- 绝对判据 `gap_abs` **保持在原始分数尺度** —— 若一并归一化，`gap_abs = 2` 在 [0,1] 空间里会永久失效

另外记录一个易误判的事实：`RERANK_GAP_ABS = 2` 在 logits 空间里**几乎永不触发**（实测最大落差 1.9994 < 2），真正起作用的是 `RERANK_GAP_RATIO`。后续做消融别只盯 `gap_abs`。

### 9.3 上下文字段转发禁用逐字段白名单

prompt 规则要求「结论后必须紧跟 `⟨条款号⟩`」，但上下文构造阶段用**逐字段白名单**拼装文档，把 `clause_no` 丢掉了 —— 模型拿不到条号，只能编（实测编出 `⟨第二条⟩`，真实条款号是 `2.3`）。

**修法**：改成 `dict(item)` **整体转发**，并在上下文里显式输出 `[条款号=…]`。

教训：新增字段是常态，白名单是负资产 —— 每加一个字段就多一处漏点，且**静默失败**。同类问题还有 `test/10` 评测台里 monkey-patch 的 rerank 副本用了同一套白名单，导致评测台与线上同源同病、看不出缺陷。

### 9.4 硬性规则必须能被上下文满足

prompt 里写的每一条硬性约束，都要能对上「上下文里真的有这个字段」。否则模型只有两条路：编造，或违反规则。**规则与数据契约必须成对 review**。

另一个相关决定：**固定免责声明在两条链路上的落地方式不同**。

| 链路 | 输出契约 | 落地方式 |
|---|---|---|
| 条款问答 | 自然语言 | prompt 硬指令：规则 8「缺失即视为不合格」 |
| 合规审查 | 严格 JSON | **代码追加** —— prompt 要求只输出 JSON，再加一条「必须追加声明」会自相矛盾，模型只能二选一 |

### 9.5 合规 prompt 必须声明「清单是筛出的子集」

负面清单 105 条不会全部塞进 prompt（全文约 5079 字 ≈ 4000 token）。如果把「从 105 条里筛出的子集」直接交给模型并说「对照它判断，没有匹配就是合规」，那么**漏召回会被模型判成「合规」** —— 这是一个**会掩盖自身错误**的方向性缺陷，在合规场景下是最危险的一侧。

**修法**：prompt 显式声明这是子集，未列出的条目需另行检索，不得据「不在清单里」下合规结论。

### 9.6 产品名必须来自台账，且 LLM 输出要清洗

`item_name` 是**三套存储共用的关联键**（条款切片 / 产品名索引 / 规则表），必须确定性。

换用新模型后，5 份文档的产品名解析返回了字符串 `'""'`。原来的判空是 `if not item_name` —— `'""'` 是**真值**，判不出来。后果：265 个切片全部塌缩到同一个键，并开始跨产品互相召回。

**修法**：`item_name` 改由**台账 `sources.csv` 的「产品名称」列**确定（该列是监管备案名，实测与历史 LLM 输出 **17/17 逐字一致**，改用它不改变任何已有数据），LLM 只作为兜底，且输出必须清洗（剥成对引号 / 去全部空白 / 空串回退）。读取统一走 `app/utils/ledger_utils.py` —— 分散在多处实现迟早会漂移。

### 9.7 抽取规则：先穷举表述变体，再下结论

理赔材料清单最初打算上 LLM 抽取，实测发现**三种标题写法加正则即可全覆盖**，且结果可复现、零成本。反过来，另外两处才是真正的坑：

- **材料抽取必须全量取池**：条款类型标签不可靠（材料条款被标成「保险费」「其他」），按 `clause_type` 过滤会**静默漏掉 3 款产品**。过滤职责交给「首条材料必须是保险合同/保险单/投保单」的形态门。
- **事故类型子串匹配必须分级排序**：「身故」是「投保人身故保险费豁免」的子串 —— 不排序会把**投保人**的材料排在**被保险人**身故保险金之前，属业务性错误。改为「精确 → 前缀 → 中间子串」三级排序并标注匹配质量。

### 9.8 意图判定用词根组合，不用长短语

用「词根 × 词根」组合判定意图（理赔词根 × 材料词根 / 时限词根 / 事故词根），禁用长短语精确匹配 —— 后者一遇表述变体就失效。并且**必须先命中理赔语义**，否则「犹豫期是多久」会被误判成理赔问题而错误路由。

### 9.9 向量字段名按集合而异

不同集合的向量字段命名不统一：条款库是 `vector` / `sparse`，产品名索引是 `dense_vector` / `sparse_vector`。传错字段名 **不会返回空结果**，而是抛 `MilvusException(1100, fieldName not found)` —— 表现是整个检索链路静默失败，任何问题都答「未找到相关产品」。

**修法**：`create_hybrid_search_requests()` 增加可配字段名参数，调用方按目标集合显式指定。

> 这个缺陷曾被「指标全绿」掩盖了很久：检索层评测直接查条款库，**绕过了产品名对齐节点**，所以 276 条用例全绿也没暴露它。教训：**指标全绿 ≠ 链路可用**。

## 10. 合规红线

以下四类问题**一律拒答**，并引导至持牌从业人员或官方客服。这既是产品边界，也是写进代码的分支：

| 禁止项 | 原因 |
|---|---|
| 产品推荐、性价比对比 | 属销售行为，需持牌资质 |
| 保费测算、投保方案建议 | 属保险销售建议 |
| 理赔金额承诺、「一定能赔 / 肯定不赔」 | 属结论性承保判断，且无法验证 |
| 泛保险知识百科式问答 | 不需要检索私有文档，RAG 价值不成立 |

此外还固化了两条工程约束：

- **联网内容不得作为条款依据**：上下文里联网条目会带显式来源标注，prompt 规则 7 禁止依据其回答任何条款内容（保险责任、保险期间、等待期、费率、申请材料、理赔时限），也禁止引用其作为条款出处。
- **免责声明强制输出**：prompt 规则 8 声明「缺失即视为不合格」，并由评测的编造检测指标持续监督。

### 已知挂账

1. **rerank 阶段评测基线从未建立** —— `test/10 --with-rerank` 默认不跑（CPU 约 17~25s/条），因此 9 月的 rerank 改动（分组 + 归一化）**没有指标层面的回归保护**，只有 e2e 用例支撑。动它之前应先存一轮基线。
2. **`INCLUDE_UNIVERSAL` 是否关闭取决于金标集扩量** —— 当前 17 条金标测不出它存在的意义（长尾条目），不建议动。
3. **单次问答 34～35s** —— HyDE 生成 + CPU rerank 是主要耗时项，计划由 3.5 上 vLLM 解决。
4. **语料仅 17 款产品** —— 目标 30–50 款。
